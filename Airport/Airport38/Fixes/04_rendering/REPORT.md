# Rendering38 implementation handoff

Implemented only in this assigned folder. No shared source, native map, live Blender scene or running Unreal session was changed by this fixer.

## Integration

- Source module: `rendering38.py`, `plan(ctx)` and `build(ctx)`. Records the intended renderer specification without covering geometry defects.
- Native module: `native38_rendering.py`, `apply_native(ctx)`, after final actor placement and airside translation. Owns creation of the final architecture and bridge lights; the importer must not independently create a second copy of `D.lights`.
- Native-only R05 refinement: `native38_rendering.refine_ceiling_fill(ctx)` may run against the already saved38 map without a mesh import. It removes only obsolete AP38 upward bounce pools and updates existing named AP38 room grades. Root saves/captures afterward. Full `apply_native` also calls this automatically.
- Runtime: copy **both** `airport_rendering38.py` and `rendering38.py` into the Python runtime directory. Call `airport_rendering38.install(G)` **last**, after every legacy/38 initializer. Only Airport38 imports it. It rejects an incorrect map revision and double installation.
- Preserve bridge `follow_actor` light records when architecture replaces `D.lights`. Root has agreed to patch assembly for this. `apply_native` attaches each moving practical to its actual sleeve using **KEEP_WORLD** for location/rotation/scale. The initial source coordinates are already world coordinates; this avoids a second translation/rotation and allows native inherited motion.
- After final Blender source synchronization, run `coplanar38.audit_blender_layout(D, R/'ArtBible/Coplanarity38.json')`. It uses evaluated mesh triangles of **active placed structural assets**, including each instance transform/scale. This must run after architecture, not during rendering's earlier source build.

## R05b native review response

I inspected the actual `16_A08Ceiling.png`, `17_A08Interior.png` and `01_Entrance.png` supplied by root. Although root reports structural temporal improvement (ceiling mean0.185/255, unchanged probe[27,31,38] across8frames), the ceiling was still almost black between obvious warm pools. That fails the intended welcoming visual condition. Enlarging a **movable** rectangular source's specular dimensions cannot make its diffuse approximation behave like broad baked indirect lighting; I replaced the local fill design instead of increasing those pools' intensity.

The refinement uses the existing Unreal Ambient Cubemap lit-material path, supported by bundled `Engine/Classes/Engine/Scene.h` (`AmbientCubemap`, intensity/tint overrides) and `Shaders/Private/AmbientCubemapComposite.usf` (diffuse/material response plus ambient occlusion). It adds a weak, constant indirect floor while direct fixtures and AO retain directional/contact depth. The HDR contains **no** clouds, bright directional dots, gradients or photographic texture, so it cannot create the prior spatial warm spots.

The grade bounds are explicitly **camera-region bounds** with12cm transition blends; they are not claimed to clip lighting to every world-space surface through a doorway. This is a restrained ambient approximation consistent with the user's acceptance of indirect fill. No ceiling emission, unlit ceiling shader, geometry change, exposure shift or AA alteration is used. The actual final ceiling brightness, material clarity and contact depth must be judged from the new native captures. These settings remain tunable from the one `ambient_specs` authority if native evidence requires a different energy level.

The first native refinement attempt failed before changing lights because I had inferred that the header's internal HDR decision cache was exposed to Python. It is not exposed in the actual engine build. The importer now uses only documented reflected `TextureFactory.supported_class=TextureCube` and `create_material=False`, the automatic long-lat `.hdr` cube route, and an explicit actual `TextureCube` class assertion. A strict mock rejects any unsupported factory field; the wrong-class existing import test must also fail. This remains an API-contract test, not proof of engine import success. See [Epic TextureFactory Python API](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/TextureFactory?application_version=5.6) and [Epic Using Cubemaps](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-cubemaps?application_version=4.27).
